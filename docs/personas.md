# Personas

## Primary: engineering lead adopting coding agents

They have several developers already using coding agents, but each setup is
personal, difficult to review, and tied to one workstation or harness. They
need a credible path from local experimentation to shared, repeatable, and
auditable agent work.

They arrive asking:

- What is AI Outfitter, in one sentence?
- Can I start without replacing my current agent tools?
- Which component should I adopt first?
- What is real today, and what is still being designed?
- Can my team own its configuration and evidence?

The site MUST answer those questions before asking them to learn project names.
It MUST make the first useful action obvious: run Outfitter or read the getting
started guide.

## Secondary: platform engineer scaling agent workloads

They are responsible for CI, Kubernetes, permissions, secrets, audit evidence,
and policy. They need architectural boundaries, status labels, and direct links
to source repositories. They distrust claims that hide operational tradeoffs.

## Secondary: agent-tool author

They build profiles, skills, extensions, evaluations, or integrations. They
need the `.agents` convention, catalog model, extension ecosystem, and clear
contribution paths.

## Content and design principles

- Lead with the adoption problem and the path through it, not the repository
  map.
- Use concrete verbs: compose, pin, run, review, capture, measure.
- Separate available software from design-stage direction.
- Prefer evidence and inspectable configuration over autonomy superlatives.
- Keep the visual system technical, warm, and field-ready: dark ink, canvas,
  signal orange, compact labels, and generous reading space.
- Every project page MUST link to its canonical repository and SHOULD link to
  its most useful upstream documentation.
